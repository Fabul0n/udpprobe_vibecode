# udpprobe

UDP-инструмент на Rust по `lecture-03-udpprobe-deck.html`: ограниченный эхо-сервер,
серии проб, лестница размеров и перебор темпа. Измерения и итоговые счётчики сервера
выводятся в JSON; диагностические сообщения идут в stderr.

## Сборка и быстрый запуск

Разработка и проверка выполнены на Rust 1.97.1, edition 2024. Установить Rust можно
через [rustup](https://www.rust-lang.org/tools/install). `Cargo.lock` хранится в Git.

```bash
cargo build --release --locked
```

Первый терминал:

```bash
./target/release/udpprobe server --addr 127.0.0.1:9999 \
  --max-echo 4096 --rate-limit 10000/s
```

Второй терминал:

```bash
./target/release/udpprobe train --to 127.0.0.1:9999 \
  --count 100 --size 1200 --rate 50pps > train.json

./target/release/udpprobe mtu --to 127.0.0.1:9999 \
  --min 512 --max 1600 --mode ladder --count 20 --repeats 2 > mtu.json

./target/release/udpprobe sweep --to 127.0.0.1:9999 \
  --size 1200 --rates 50,100,500,1000pps --count 100 --repeats 2 > sweep.json
```

Ctrl-C останавливает отправку, сохраняет частичный JSON и завершает процесс кодом
130. На сервере Ctrl-C также выводит итоговые счётчики. `server --duration 10`
автоматически завершает сервер через 10 секунд с кодом 0. Счётчики работающего
сервера каждые 5 секунд печатаются в stderr.

Справка: `udpprobe --help`, `udpprobe train --help` и аналогично для остальных команд.
Адреса — числовые `IP:port`; IPv6: `--to '[::1]:9999'` и `--addr '[::1]:9999'`.
DNS не используется, чтобы адрес измеряемого пути был явным.

## Параметры эксперимента

- `--count`: число проб на одну серию, по умолчанию 100, максимум 1 000 000.
- `--rate`: целое число pps, формы `50`, `50pps`, `50/s`; диапазон 1..100000.
- `--timeout-ms`: отдельный deadline каждой пробы, 1..60000 мс, по умолчанию 1000.
- `--size`: полный UDP payload, включая наш заголовок; 23..65507 байт.
- `--token`: необязательный u64 в decimal/`0x` hex. Должен совпадать на обеих сторонах;
  минимальный payload становится 31 байт. Token передаётся открытым текстом,
  не является криптографической аутентификацией и не попадает в JSON.
- `--echo-small`: запрос полного размера, ответ только из заголовка. Позволяет
  уменьшить влияние размера ответа, но не доказывает направление потери.
- `mtu --step N`: своя лестница размеров. Без `--step` используются точки лекции
  512, 1024, 1200, 1280, 1400, 1472, 1600, 2048, 4096 внутри диапазона и его концы.
- `--repeats`: для mtu/sweep, 1..10, по умолчанию 2. Каждая серия имеет отдельный
  JSON-результат и новый локальный UDP-сокет.

План серии ограничен 600 секундами отправки, всего эксперимента — часом и 256
сериями. Это ограничения планового времени: замедление ОС может удлинить запуск.
Размер 65507 выбран как общий консервативный максимум для обычного IPv4/IPv6 UDP.
Фактический предел пути может быть меньше.

Сервер по умолчанию слушает localhost, отвечает максимум 1200 байт и 200 раз/с.
Превышение `--max-echo` приводит к отбрасыванию, а не усечению. `--echo-small`
сравнивает с лимитом размер малого ответа. Темп ограничен одновременно глобально
и на адрес отправителя минимальным интервалом; всплесков после задержки нет.
Таблица адресов ограничена `--max-peers` (4096), старые записи освобождаются после
60 секунд неактивности при заполнении таблицы. Сервер не отвечает на response,
невалидный пакет или несовпадающий token. Ответ не больше запроса.

## Что означают результаты

JSON имеет `schema_version: 1`, входные параметры, массив `trials`, наблюдения и
ограничения интерпретации. Одинаковая схема и конфигурация обеспечивают повторяемую
процедуру, но реальные RTT и потери не обязаны совпадать между запусками.

- `attempted = sent + send_errors`. Отправлено означает, что ОС приняла датаграмму.
- `lost`: успешно отправленные пробы без корректного ответа к их deadline.
- `unanswered_at_cancel`: пробы без ответа, deadline которых при отмене ещё не истёк.
- `sent = received_unique + lost + unanswered_at_cancel`.
- `loss_ratio = lost / sent`; при отсутствии успешных отправок — `null`.
- `duplicates`: дополнительные корректные ответы на уже отвеченную пробу до её deadline.
  `duplicate_ratio = duplicates / (received_unique + duplicates)`.
- `reordered`: первые своевременные ответы с seq меньше максимального уже принятого seq.
  `reorder_ratio = reordered / received_unique`.
- `late_responses`: ответы после индивидуального deadline, замеченные до конца серии.
  Не уменьшают `lost`. После конечного окна наблюдения ответы не учитываются.
- `invalid_responses`: неверный формат, адрес, тип, seq, timestamp, flags, token или размер.
- `receive_errors`/`first_receive_error`: наблюдаемые ошибки сокета, например ICMP
  port-unreachable на connected UDP. Фатальные ошибки ввода-вывода завершают команду
  ненулевым кодом; JSON незавершённого эксперимента в этом случае не гарантируется.
- RTT считается по локальным монотонным часам от попытки отправки до чтения ответа.
  Unix timestamp используется для сопоставления ответа, а не вычисления RTT.
- `rtt`: min/mean/p50/p95/p99/max/stddev в миллисекундах; при отсутствии ответов `null`.
  Percentiles — nearest rank, jitter — population standard deviation RTT.
- `achieved_rate_pps`: успешные отправки / (время между первой и последней успешными
  отправками + один запрошенный интервал). Сравнивайте с `requested_rate_pps`.
- `goodput_bytes_per_second`: байты уникальных своевременных response UDP payload
  / полное время серии, включая ожидание последнего deadline. Это не скорость канала.

`mtu` не выставляет DF и не управляет PMTUD. Порог размера — наблюдение, а не доказанный
MTU. Рост потерь при `sweep` может объясняться серверным лимитом, сокетными очередями,
планировщиком клиента или сетью. Сопоставляйте JSON клиента со счётчиками сервера.
Синхронный клиент одновременно обслуживает отправку и чтение через неблокирующий
сокет; polling до 100 мкс и планировщик ОС ограничивают точность высокого rate.

## Проверки

```bash
cargo fmt --check
cargo clippy --locked --all-targets -- -D warnings
cargo test --locked
cargo build --release --locked
```

`tests/experiments.rs` использует виртуальное время: управляемые потери, задержки,
дубликаты, перестановки, ошибки отправки, отмена и лимиты. Один и тот же `run_trial`
работает с FakeNetwork и RealUdpConn. `tests/cli.rs` запускает настоящий бинарник
на IPv4/IPv6 loopback (IPv6 пропускается, если недоступен). Внешняя сеть не нужна.

CI в `.github/workflows/ci.yml` запускает форматирование, Clippy, тесты и release-сборку.
Go-команда `go test -race` из лекции здесь неприменима: используется Rust и однопоточное
состояние измерений; это не заявление о выполнении ThreadSanitizer.

## С чего читать код

1. `src/probe/mod.rs` — исходный учебный `Probe`, формат и проверка пакетов.
2. `src/server.rs` — политика эхо-ответов, лимиты, счётчики.
3. `src/transport.rs` — trait PacketConn, реальный сокет и часы.
4. `src/client.rs` — планирование, сопоставление ответов и deadline.
5. `src/report.rs` — статистика и схема JSON.
6. `src/main.rs` — clap, сборка параметров, сигналы и вывод.
7. `tests/experiments.rs` — FakeNetwork и ожидаемые результаты экспериментов.

Подробности формата: [docs/protocol.md](docs/protocol.md).
Отчёт проверки: [docs/verification.md](docs/verification.md).
Публикация на GitVerse и добавление участника из задания выполняются отдельно.
