Адрес — значение, сеть — интерфейс.

Rate limit в обе стороны

Темп контролирует инструмент, а не сеть.

ticker := time.NewTicker(interval) defer ticker.Stop() for seq := uint64(0); seq < count; seq++ { select { case <-ticker.C: sendProbe(seq) case <-ctx.Done(): return ctx.Err() } }

Лимиты в обе стороны

  • Клиент не должен превращаться в шторм
  • Сервер не отвечает быстрее, чем разрешено: token bucket или минимальный интервал между ответами на один адрес

Если инструмент не контролирует темп, он измеряет не сеть, а собственную невоспитанность.

Эксперимент 2 · длинный train с фиксированным rate

Разбираем результат по seq.

type probeResult struct { seq uint64 sentAt time.Time gotAt time.Time responded bool duplicate int rtt time.Duration }

Что считаем по ответам

  • потери (loss) — seq отправлен, ответа нет до deadline
  • duplicate — на один seq пришло больше одного ответа
  • reorder — ответ на seq=N пришёл после ответа на seq=N+k
  • RTT — gotAt − sentAt
  • jitter — разброс RTT, не только среднее
лекция 03 · udpprobe19
Тайминг: 1:24–1:40. Вторая задача: отправить длинный train с фиксированным rate и разобрать результат. Клиент хранит probeResult на каждую пробу. По ответам считаем потери (loss), duplicate, reorder, RTT и jitter — разброс RTT, не только среднее.

Ключевая ловушка

Потеря пробы ≠ потеря UDP request.

01request потерян

Сервер пробу вообще не видел.

02response потерян

Сервер ответил, но ответ не доехал.

03server rate limit

Сервер отбросил пробу по собственному лимиту.

04client не успел

Ответ пришёл, но клиент не успел его прочитать.

В отчёте пишем не «UDP потерял 3%», а «3% проб не получили response до deadline при таких-то условиях».
